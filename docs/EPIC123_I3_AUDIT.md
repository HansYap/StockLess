1. **US1.2 AC2：供应商比较。** `backend/src/supplier-order.ts:6` 只有箱规、最低订单、交期三个条件，`suggestSupplierOrder` 为单一条件组调整数量。`frontend/src/screens/PurchasePlanScreen.tsx:11` 每商品只保存一组条件。需要至少两个可比较的供应商方案及其结果，并在样例中能实际体验。完整比较功能与 E6 有交叉，但 E1 的样例 AC 仍必须满足。
2. **US1.6 AC3：所有标签可搜索。** `frontend/src/readiness/model.ts:33` 选取一个代表名称，`frontend/src/screens/ReadinessOverview.tsx:33` 只搜索该名称、代码及包装。核查复现：同一 SKU A，名称 Tea Original/Tea Alternate，后端保留两行标签并排除冲突记录，但商品列表搜索 Tea Alternate 的匹配数为 0。需要汇总标签集合，用于显示及搜索；保持冲突阻断规则。
3. **US1.7：存储解释。** `backend/src/field-registry.ts:212` 有简短隐私说明，`frontend/src/components/SavedDataControls.tsx:31` 有管理和删除控制，但没有完整覆盖“打开解释→列出数据/设置/计划/决策/结果及用途→管理保存内容”，也没有清除浏览器数据可能丢失的提示。`PRIVACY_NOTICE.persistence` 当前没有被 UI 使用。需要完善解释入口与内容，并连接既有管理控制。
4. **US2.4 AC2：默认问题下载。** `frontend/src/screens/ReadinessScreen.tsx:29` 的 `findingsCsv` 对已处理项目使用“See all row evidence…”代替逐记录 Used/Left out。完整业务引擎报告存在，但默认 Download list 是另一个分组报告。需要展开相关源行及各自状态，或将下载入口接到符合条款的报告；库存新鲜度生成的汇总项也应保持来源可追溯。

## 补齐顺序（Impact Dashboard 暂缓）

以下是待实施步骤，不是本次已完成的代码变更。

1. **先补标签证据与搜索。** 从每商品的来源行汇总去重名称、代码、包装标签，在就绪及采购视图显示并搜索完整集合；身份冲突仍阻断该商品预测和采购。验收：冲突中的任一名称都能找到相同商品，原始源行可追溯，未冲突商品不受影响。
2. **统一问题下载的逐行证据。** 默认下载复用业务引擎报告，或依据 snapshot 将分组源行展开，逐行写出 Used/Left out、字段、源列、来源文件/工作表、原因和动作；过滤下载保留正确的源行范围。验收：同组重复的保留行标 Used，排除副本标 Left out；正常交易不误排除；无问题说明正确。
3. **完善存储解释并连接管理控制。** 在保存/使用已保存工作前提供解释入口，列出各类数据及用途，明确属于当前浏览器和清除浏览器数据的丢失风险；解释中可进入既有 inspect/delete/Clear Everything。验收：普通浏览器保存、重开、删除及清空都可验证。
4. **修正采购页无评估汇总。** 分开计数可评估订单与多余库存订单，不用正多余量数组是否为空判断结果存在。无订单显示 Not entered，订单不可评估显示 Unavailable+原因/动作；有可评估订单且无多余才显示 0。验收覆盖空订单、真实零、全部不可评估、部分可评估四种情况。只修改采购页，保持 Impact Dashboard 原样。
5. **补样例供应商比较。** 将单组条件扩展为多个可比较方案，复用同一份需求/库存证据，分别输出箱规/MOQ调整后的数量、到货日期、周期提示及可比结果；先在采购流程提供比较入口。金额比较须确认供应商报价来源及单位，不能把 MOQ 或交期臆造为价格。样例提供至少两个条件不同的方案。该项是 US1.2 AC2 的跨 E6 依赖，即使暂缓完整 E6，E1 样例的比较仍需完成。
6. **最后完成限定页面的字体与真实验收。** 在 Upload、Mapping、Readiness、Purchase、Storage 页面按 V3.1 角色修正局部排版并验多语言；不调整 Impact 页面及会影响它的共享样式。收集真实文件并建立人工答案集，再补浏览器下载、持久保存、容量/取消和网络记录证据。

## 正式测试需要哪些文件

需要符合约定业务口径的正向文件，也需要包含错误的反向文件。不要先把所有商户表头改成统一模板，否则无法验证 column mapping 对真实导出的适应能力。

1. **真实列匹配基准：至少 12 份脱敏 CSV。** 原文此前 US1.4 AC7 明确要求英文和马来文表头，含缩写与不明确表头；涵盖销售日期、商品名称、销量、库存和库存日期。每份提供正确字段答案与人工预期。要求已建议必需字段准确率为 1.00，系统自行确认数为 0，覆盖率另外报告。XLS/XLSX 可以增加测试，但不能替代这项 CSV 集要求。
2. **真实 Excel 导出：XLS 和 XLSX 都要。** 包括单表、多表、空表、日期格式、表头偏移、前导零商品代码及实际商户常见格式。标注应选择的工作表、记录数、原始行号及预期映射。
3. **正向数据口径。** 必需：销售日期、商品代码或名称+包装标识、销量。库存及库存日期支持库存/采购分析；Unit Cost 为 MYR 的采购成本，与销售/库存使用同一单位，同商品/包装的非空值合法且一致。缺少可选成本不阻止数量分析。预测仍使用正销量，负销量作为退货保留。
4. **覆盖时间与边界。** 提供相对测试分析日期的最近八个完整周、四到七个完整周、少于四周；不要将未知周补为零。另测重复与不同交易、身份冲突、非法/歧义日期、库存过期/未来日期、成本为空/0/负值/不一致、更改映射后重验。边界案例可用合成文件，真实 CSV 基准不可由合成文件替代。
5. **普通目标浏览器验收。** 验证持久保存与重新打开、真实问题 CSV 下载、容量/进度/取消、AI 加载失败仍能手动匹配、网络记录没有商户字段和记录外发，以及全部支持语言的可见性。

当前架构是浏览器本地 TypeScript 业务引擎及 Worker，没有 HTTP 服务和服务器数据库。开展这些测试不需要提供数据库账号或 API key；需要文件、字段答案、单位口径和预期结果。
